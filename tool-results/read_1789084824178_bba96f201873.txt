    26→    26→## 1. 시스템 전체 구조
    27→    27→
    28→    28→### 1.1 아키텍처 개요
    29→    29→
    30→    30→관리자 대시보드는 **기존 Next.js 16 키오스크 애플리케이션 내에 `/admin/*` 경로로 통합**되는 모듈이다. 별도 프로세스나 포트 없이 동일한 SQLite 데이터베이스와 Prisma 클라이언트를 공유하며, 관리자가 변경한 CMS 콘텐츠가 키오스크 프론트엔드에 실시간으로 반영되는 구조를 갖는다.

    99→    99→### 1.3 관리자→키오스크 변경 전파 흐름
   100→   100→
   101→   101→```
   102→   102→┌──────────────┐     ① 저장      ┌──────────────────┐     ② Prisma WRITE     ┌──────────┐
   103→   103→│  Admin UI    │ ──────────────► │ POST /api/admin/ │ ─────────────────────► │ CmsContent│
   104→   104→│  (편집 폼)   │                 │ cms/:key         │                        │  (SQLite) │
   105→   105→└──────────────┘                 └──────────────────┘                        └────┬─────┘
   106→   106→                                                                                    │
   107→   107→                                               ③ 키오스크 폴링 (3s 간격)             │
   108→   108→┌──────────────┐     ⑥ Re-render  ┌───────────────┐    ⑤ Zustand set()   ┌────▼─────┐
   109→   109→│  Kiosk UI    │ ◄─────────────── │ useCmsStore   │ ◄──────────────────  │ GET      │
   110→   110→│  (IdleScreen │                   │ (Zustand)     │    ④ JSON + ETag     │ /api/cms/│
   111→   111→│   etc.)      │                   └───────────────┘                       │ content  │
   112→   112→└──────────────┘                                                            └──────────┘
   113→   113→```
   114→   114→
   115→   115→| 단계 | 설명 | 지연 |
   116→   116→|------|------|------|
   117→   117→| ① | 관리자가 편집 폼에서 값 변경 후 "저장" 클릭 | 사용자 액션 |
   118→   118→| ② | Admin API가 Prisma로 `CmsContent` 테이블에 UPSERT | ~5ms |
   119→   119→| ③ | 키오스크 프론트엔드가 3초 간격으로 `GET /api/cms/content` 폴링 | ≤3s |
   120→   120→| ④ | 서버가 ETag 기반 변경 감지, 변경 시에만 새 데이터 응답 (304 아니면 200) | ~2ms |
   121→   121→| ⑤ | Zustand `useCmsStore.setCmsContent()` 호출로 전역 상태 갱신 | ~1ms |
   122→   122→| ⑥ | React가 상태 변경 감지, 해당 CMS 값을 사용하는 컴포넌트만 Re-render | ~16ms |
   123→   123→
   124→   124→**총 전파 지연**: CMS 저장 후 **≤3초** 내 키오스크 화면에 반영 보장

   436→   436→
   437→   437→```
   438→   438→┌──────────────┐                                           ┌──────────────────┐
   439→   439→│  /admin/login│                                           │  AdminUser Table  │
   440→   440→│  (이메일 +   │                                           │  email            │

   459→   459→       Set-Cookie: admin_access_token=<jwt>; HttpOnly; Secure; SameSite=Strict; Path=/admin; Max-Age=900

   484→   484→### 4.3 세션 관리 전략
   485→   485→
   486→   486→```
   487→   487→┌───────────────────────────────────────────────────────────────┐
   488→   488→│                     세션 라이프사이클                          │
   489→   489→│                                                               │
   490→   490→│  [로그인]                                                     │
   491→   491→│    │  Access Token 발급 (15분)                                │
   492→   492→│    │  Refresh Token 발급 (7일)                                │
   493→   493→│    │  httpOnly 쿠키 2개 설정                                  │
   494→   494→│    ▼                                                          │
   495→   495→│  [API 요청]                                                   │
   496→   496→│    │  Authorization: Bearer <access_token>                    │
   497→   497→│    │  ├─ 유효 → 요청 처리                                     │
   498→   498→│    │  ├─ 만료 (401) → Refresh Token으로 자동 갱신              │
   499→   499→│    │  └─ 무효 → 401 → /admin/login 리다이렉트                 │
   500→   500→│    ▼                                                          │
   501→   501→│  [비활동 감지]                                                │
   502→   502→│    │  30분間 사용자 액션 없음                                  │
   503→   503→│    │  → 자동 로그아웃 → /admin/login                          │
   504→   504→│    ▼                                                          │
   505→   505→│  [명시적 로그아웃]                                             │
   506→   506→│       쿠키 삭제 + AuditLog 기록 (LOGOUT 이벤트)               │
   507→   507→└───────────────────────────────────────────────────────────────┘
   508→   508→```
   509→   509→
   510→   510→| 항목 | 값 | 설명 |
   511→   511→|------|-----|------|
   512→   512→| Access Token 수명 | **15분** | 짧은 수명으로 탈취 피해 최소화 |
   513→   513→| Refresh Token 수명 | **7일** | 장기 세션 유지 (자동 갱신) |
   514→   514→| 비활동 로그아웃 | **30분** | 마지막 API 요청 후 30분 경과 시 자동 로그아웃 |
   515→   515→| 비밀번호 정책 | 8자 이상, 대소문자+숫자+특수문자 | Zod 스키마 검증 |
   516→   516→| 로그인 실패 잠금 | 5회 연속 실패 시 15분 잠금 | brute-force 방어 |
   517→   517→| 쿠키 속성 | `HttpOnly; Secure; SameSite=Strict` | XSS·CSRF 방어 |
   518→   518→
   519→   519→### 4.4 RBAC 권한 체크 미들웨어
   520→   520→
   521→   521→```typescript
   522→   522→// src/lib/admin-rbac.ts
   523→   523→
   524→   524→type AdminRole = 'super_admin' | 'admin' | 'operator';
   525→   525→
   526→   526→// 리소스-액션 권한 매핑
   527→   527→const RBAC_TABLE: Record<AdminRole, Record<string, string[]>> = {
   528→   528→  super_admin: {
   529→   529→    // 모든 리소스에 모든 액션 허용
   530→   530→    cms:       ['read', 'write'],
   531→   531→    books:     ['read', 'write', 'delete'],
   532→   532→    users:     ['read', 'write', 'delete'],
   533→   533→    accounts:  ['read', 'write', 'delete'],
   534→   534→    audit:     ['read', 'export'],
   535→   535→    settings:  ['read', 'write'],
   536→   536→    dashboard: ['read'],
   537→   537→  },
   538→   538→  admin: {
   539→   539→    cms:       ['read', 'write'],
   540→   540→    books:     ['read', 'write', 'delete'],
   541→   541→    users:     ['read', 'write', 'delete'],
   542→   542→    accounts:  [],                   // 계정 관리 불가
   543→   543→    audit:     ['read'],             // 내보내기 불가
   544→   544→    settings:  ['read'],             // 쓰기 불가 (대출 규칙은 cms 채널로)
   545→   545→    dashboard: ['read'],
   546→   546→  },
   547→   547→  operator: {
   548→   548→    cms:       ['read'],             // 읽기 전용
   549→   549→    books:     ['read'],
   550→   550→    users:     ['read'],
   551→   551→    accounts:  [],
   552→   552→    audit:     [],
   553→   553→    settings:  ['read'],
   554→   554→    dashboard: ['read'],
   555→   555→  },
   556→   556→};
   557→   557→
   558→   558→export function checkPermission(
   559→   559→  role: AdminRole,
   560→   560→  resource: string,
   561→   561→  action: string
   562→   562→): boolean {
   563→   563→  return RBAC_TABLE[role]?.[resource]?.includes(action) ?? false;
   564→   564→}
   565→   565→```
   566→   566→
   567→   567→```typescript
   568→   568→// src/lib/admin-middleware.ts — API Route 공통 미들웨어
   569→   569→
   570→   570→import { verifyToken } from './admin-auth';
   571→   571→import { checkPermission } from './admin-rbac';
   572→   572→import { logAudit } from './audit';
   573→   573→
   574→   574→export async function withAdminAuth(
   575→   575→  request: NextRequest,
   576→   576→  handler: (req: NextRequest, admin: AdminUser) => Promise<NextResponse>,
   577→   577→  options: { resource: string; action: string }
   578→   578→): Promise<NextResponse> {
   579→   579→  // ① JWT 검증
   580→   580→  const token = request.cookies.get('admin_access_token')?.value;
   581→   581→  const payload = verifyToken(token);
   582→   582→  if (!payload) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });
   583→   583→
   584→   584→  // ② AdminUser 조회 (isActive 확인)
   585→   585→  const admin = await db.adminUser.findUnique({ where: { id: payload.sub } });
   586→   586→  if (!admin || !admin.isActive) {
   587→   587→    return NextResponse.json({ error: 'Forbidden' }, { status: 403 });
   588→   588→  }
   589→   589→
   590→   590→  // ③ RBAC 권한 체크
   591→   591→  if (!checkPermission(admin.role, options.resource, options.action)) {
   592→   592→    return NextResponse.json({ error: 'Insufficient permissions' }, { status: 403 });
   593→   593→  }
   594→   594→
   595→   595→  // ④ 핸들러 실행
   596→   596→  const response = await handler(request, admin);
   597→   597→
   598→   598→  // ⑤ 쓰기 작업 시 감사 로그 기록 (after hook)
   599→   599→  if (['POST', 'PATCH', 'DELETE'].includes(request.method)) {
   600→   600→    await logAudit(request, admin, response);
   601→   601→  }
   602→   602→
   603→   603→  return response;
   604→   604→}
   605→   605→```

   761→   761→## 6. 실시간 동기화 아키텍처
   762→   762→
   763→   763→### 6.1 폴링 전략 개요
   764→   764→
   765→   765→키오스크 프론트엔드가 관리자의 CMS 변경 사항을 실시간으로 감지하기 위해 **3초 간격 HTTP 폴링 + ETag 캐싱** 전략을 사용한다. WebSocket 대비 구현 복잡도가 낮고, 단일 키오스크 환경에서 충분한 실시간성(≤3초)을 보장한다.
   766→   766→
   767→   767→```
   768→   768→┌──────────────────────────────────────────────────────────────────┐
   769→   769→│                    폴링 라이프사이클                             │
   770→   770→│                                                                  │
   771→   771→│  [초기 로드]                                                     │
   772→   772→│    GET /api/cms/content                                          │
   773→   773→│    → 200 OK, ETag: "abc123", Body: { ... 모든 CMS 키-값 ... }   │
   774→   774→│    → useCmsStore 초기화                                           │
   775→   775→│                                                                  │
   776→   776→│  [폴링 루프] (3초 간격)                                          │
   777→   777→│    ┌──────────────────────────────────────────┐                  │
   778→   778→│    │  GET /api/cms/content                    │                  │
   779→   779→│    │  If-None-Match: "abc123"                 │                  │
   780→   780→│    │                                          │                  │
   781→   781→│    │  ├── 304 Not Modified                    │                  │
   782→   782→│    │  │   → 변경 없음, 다음 폴링 대기           │                  │
   783→   783→│    │  │                                      │                  │
   784→   784→│    │  └── 200 OK, ETag: "def456"             │                  │
   785→   785→│    │      Body: { ... 갱신된 CMS 키-값 ... }  │                  │
   786→   786→│    │      → useCmsStore 업데이트               │                  │
   787→   787→│    │      → React Re-render                   │                  │
   788→   788→│    └──────────────────────────────────────────┘                  │
   789→   789→│                                                                  │
   790→   790→│  [에러 처리]                                                     │
   791→   791→│    ├── 네트워크 오류 → 5초 후 재시도 (지수 백오프, 최대 30초)     │
   792→   792→│    ├── 5xx 서버 오류 → 10초 후 재시도                             │
   793→   793→│    └── 3회 연속 실패 → "연결 끊김" 인디케이터 표시                │
   794→   794→└──────────────────────────────────────────────────────────────────┘
   795→   795→```
   796→   796→
   797→   797→### 6.2 ETag 기반 변경 감지
   798→   798→
   799→   799→```typescript
   800→   800→// src/app/api/cms/content/route.ts
   801→   801→
   802→   802→import { db } from '@/lib/db';
   803→   803→
   804→   804→// 서버 측 ETag 생성 (모든 CmsContent updatedAt의 해시)
   805→   805→function generateEtag(items: CmsContent[]): string {
   806→   806→  const hash = items
   807→   807→    .map(i => `${i.key}:${i.updatedAt.getTime()}`)
   808→   808→    .join('|');
   809→   809→  return `"${Buffer.from(hash).toString('base64').slice(0, 32)}"`;
   810→   810→}
   811→   811→
   812→   812→export async function GET(request: NextRequest) {
   813→   813→  const allContent = await db.cmsContent.findMany({
   814→   814→    orderBy: { key: 'asc' },
   815→   815→  });
   816→   816→
   817→   817→  const etag = generateEtag(allContent);
   818→   818→
   819→   819→  // 클라이언트 ETag와 동일 → 변경 없음
   820→   820→  const clientEtag = request.headers.get('If-None-Match');
   821→   821→  if (clientEtag === etag) {
   822→   822→    return new NextResponse(null, { status: 304, headers: { ETag: etag } });
   823→   823→  }
   824→   824→
   825→   825→  // 변경 있음 → 새 데이터 응답
   826→   826→  const contentMap = Object.fromEntries(
   827→   827→    allContent.map(c => [c.key, c.value])
   828→   828→  );
   829→   829→
   830→   830→  return NextResponse.json(contentMap, {
   831→   831→    headers: {
   832→   832→      'ETag': etag,
   833→   833→      'Cache-Control': 'no-cache',
   834→   834→    },
   835→   835→  });
   836→   836→}
   837→   837→```
   838→   838→
   839→   839→### 6.3 CMS 폴링 훅
   840→   840→
   841→   841→```typescript
   842→   842→// src/hooks/use-cms-polling.ts
   843→   843→
   844→   844→import { useEffect, useRef, useCallback } from 'react';
   845→   845→import { useCmsStore } from '@/stores/useCmsStore';
   846→   846→
   847→   847→const POLL_INTERVAL = 3000; // 3초
   848→   848→const MAX_RETRY_DELAY = 30000; // 최대 30초
   849→   849→
   850→   850→export function useCmsPolling() {
   851→   851→  const { etag, setContent, setEtag, setConnectionStatus } = useCmsStore();
   852→   852→  const retryDelay = useRef(3000);
   853→   853→  const abortController = useRef<AbortController | null>(null);
   854→   854→
   855→   855→  const poll = useCallback(async () => {
   856→   856→    try {
   857→   857→      abortController.current = new AbortController();
   858→   858→
   859→   859→      const res = await fetch('/api/cms/content', {
   860→   860→        headers: etag ? { 'If-None-Match': etag } : {},
   861→   861→        signal: abortController.current.signal,
   862→   862→      });
   863→   863→
   864→   864→      if (res.status === 304) {
   865→   865→        // 변경 없음
   866→   866→        retryDelay.current = POLL_INTERVAL; // 백오프 리셋
   867→   867→        setConnectionStatus('connected');
   868→   868→        return;
   869→   869→      }
   870→   870→
   871→   871→      if (res.ok) {
   872→   872→        const data = await res.json();
   873→   873→        const newEtag = res.headers.get('ETag') || '';
   874→   874→
   875→   875→        setContent(data);
   876→   876→        setEtag(newEtag);
   877→   877→        setConnectionStatus('connected');
   878→   878→        retryDelay.current = POLL_INTERVAL; // 백오프 리셋
   879→   879→      }
   880→   880→    } catch (err) {
   881→   881→      // 네트워크 오류 → 지수 백오프
   882→   882→      retryDelay.current = Math.min(retryDelay.current * 1.5, MAX_RETRY_DELAY);
   883→   883→      setConnectionStatus('disconnected');
   884→   884→    }
   885→   885→  }, [etag, setContent, setEtag, setConnectionStatus]);
   886→   886→
   887→   887→  useEffect(() => {
   888→   888→    // 초기 로드
   889→   889→    poll();
   890→   890→
   891→   891→    // 폴링 루프
   892→   892→    const interval = setInterval(poll, POLL_INTERVAL);
   893→   893→
   894→   894→    return () => {
   895→   895→      clearInterval(interval);
   896→   896→      abortController.current?.abort();
   897→   897→    };
   898→   898→  }, [poll]);
   899→   899→}
   900→   900→```
   901→   901→
   902→   902→### 6.4 CMS Zustand 스토어
   903→   903→
   904→   904→```typescript
   905→   905→// src/stores/useCmsStore.ts
   906→   906→
   907→   907→import { create } from 'zustand';
   908→   908→import { devtools } from 'zustand/middleware';
   909→   909→
   910→   910→type ConnectionStatus = 'connected' | 'disconnected' | 'checking';
   911→   911→
   912→   912→interface CmsState {
   913→   913→  /** CMS 콘텐츠 맵 (key → value) */
   914→   914→  content: Record<string, string>;
   915→   915→  /** 현재 ETag (변경 감지용) */
   916→   916→  etag: string | null;
   917→   917→  /** 서버 연결 상태 */
   918→   918→  connectionStatus: ConnectionStatus;
   919→   919→  /** 콘텐츠 버전 (변경 시마다 증가) */
   920→   920→  version: number;
   921→   921→
   922→   922→  // Actions
   923→   923→  setContent: (content: Record<string, string>) => void;
   924→   924→  setEtag: (etag: string) => void;
   925→   925→  setConnectionStatus: (status: ConnectionStatus) => void;
   926→   926→  /** 특정 키의 값 조회 (기본값 폴백) */
   927→   927→  getValue: (key: string, defaultValue?: string) => string;
   928→   928→}
   929→   929→
   930→   930→export const useCmsStore = create<CmsState>()(
   931→   931→  devtools((set, get) => ({
   932→   932→    content: {},
   933→   933→    etag: null,
   934→   934→    connectionStatus: 'checking',
   935→   935→    version: 0,
   936→   936→
   937→   937→    setContent: (content) => set((state) => ({
   938→   938→      content,
   939→   939→      version: state.version + 1,
   940→   940→    })),
   941→   941→
   942→   942→    setEtag: (etag) => set({ etag }),
   943→   943→
   944→   944→    setConnectionStatus: (connectionStatus) => set({ connectionStatus }),
   945→   945→
   946→   946→    getValue: (key, defaultValue = '') => {
   947→   947→      return get().content[key] ?? defaultValue;
   948→   948→    },

  1125→  1125→### 8.1 Admin API Route 패턴
  1126→  1126→
  1127→  1127→모든 `/api/admin/*` Route Handler는 `withAdminAuth` 미들웨어를 통해 인증·인가·감사 로깅을 일관되게 적용한다.
  1128→  1128→
  1129→  1129→```typescript
  1130→  1130→// src/app/api/admin/cms/[key]/route.ts
  1131→  1131→
  1132→  1132→import { NextRequest, NextResponse } from 'next/server';
  1133→  1133→import { withAdminAuth } from '@/lib/admin-middleware';
  1134→  1134→import { db } from '@/lib/db';
  1135→  1135→import { z } from 'zod';
  1136→  1136→
  1137→  1137→// Zod 입력 스키마
  1138→  1138→const UpdateCmsSchema = z.object({
  1139→  1139→  value: z.string().max(5000),
  1140→  1140→});
  1141→  1141→
  1142→  1142→export async function PATCH(
  1143→  1143→  request: NextRequest,
  1144→  1144→  { params }: { params: Promise<{ key: string }> }
  1145→  1145→) {
  1146→  1146→  const { key } = await params;
  1147→  1147→
  1148→  1148→  return withAdminAuth(request, async (req, admin) => {
  1149→  1149→    // ① 입력 검증
  1150→  1150→    const body = await req.json();
  1151→  1151→    const parsed = UpdateCmsSchema.safeParse(body);
  1152→  1152→    if (!parsed.success) {
  1153→  1153→      return NextResponse.json(
  1154→  1154→        { error: 'Validation failed', details: parsed.error.flatten() },
  1155→  1155→        { status: 400 }
  1156→  1156→      );
  1157→  1157→    }
  1158→  1158→
  1159→  1159→    // ② 변경 전 값 조회 (감사 로그용)
  1160→  1160→    const before = await db.cmsContent.findUnique({ where: { key } });
  1161→  1161→
  1162→  1162→    // ③ UPSERT
  1163→  1163→    const updated = await db.cmsContent.upsert({
  1164→  1164→      where: { key },
  1165→  1165→      create: {
  1166→  1166→        key,
  1167→  1167→        type: inferTypeFromKey(key), // cms-schema.ts에서 추론
  1168→  1168→        value: parsed.data.value,
  1169→  1169→        updatedBy: admin.id,
  1170→  1170→      },
  1171→  1171→      update: {
  1172→  1172→        value: parsed.data.value,
  1173→  1173→        updatedBy: admin.id,
  1174→  1174→      },
  1175→  1175→    });
  1176→  1176→
  1177→  1177→    // ④ 응답 (감사 로그는 withAdminAuth after hook에서 자동 기록)
  1178→  1178→    return NextResponse.json({
  1179→  1179→      key: updated.key,
  1180→  1180→      value: updated.value,
  1181→  1181→      updatedAt: updated.updatedAt,
  1182→  1182→    });
  1183→  1183→  }, { resource: 'cms', action: 'write' });
  1184→  1184→}
  1185→  1185→```

  1217→  1217→
  1218→  1218→```typescript
  1219→  1219→// src/app/api/cms/content/route.ts
  1220→  1220→
  1221→  1221→import { NextRequest, NextResponse } from 'next/server';
  1222→  1222→import { db } from '@/lib/db';
  1223→  1223→
  1224→  1224→export async function GET(request: NextRequest) {
  1225→  1225→  // ① 모든 CmsContent 조회
  1226→  1226→  const allContent = await db.cmsContent.findMany({
  1227→  1227→    select: { key: true, value: true, updatedAt: true },
  1228→  1228→    orderBy: { key: 'asc' },
  1229→  1229→  });
  1230→  1230→
  1231→  1231→  // ② ETag 생성
  1232→  1232→  const etag = generateEtag(allContent);
  1233→  1233→
  1234→  1234→  // ③ 변경 없으면 304
  1235→  1235→  const clientEtag = request.headers.get('If-None-Match');
  1236→  1236→  if (clientEtag === etag) {
  1237→  1237→    return new NextResponse(null, {
  1238→  1238→      status: 304,
  1239→  1239→      headers: { ETag: etag },
  1240→  1240→    });
  1241→  1241→  }
  1242→  1242→
  1243→  1243→  // ④ key→value 맵으로 변환
  1244→  1244→  const contentMap = Object.fromEntries(
  1245→  1245→    allContent.map(c => [c.key, c.value])
  1246→  1246→  );
  1247→  1247→
  1248→  1248→  // ⑤ 응답
  1249→  1249→  return NextResponse.json(contentMap, {
  1250→  1250→    headers: {
  1251→  1251→      ETag: etag,
  1252→  1252→      'Cache-Control': 'no-cache',
  1253→  1253→    },
  1254→  1254→  });
  1255→  1255→}
  1256→  1256→```

  1436→  1436→### ADR-D01: 동일 Next.js 프로세스 내 관리자 대시보드 통합 (별도 앱 분리 안 함)
  1437→  1437→
  1438→  1438→```
  1439→  1439→┌─────────────────────────────────────────────────────────────┐
  1440→  1440→│ ADR-D01: Same Next.js Process                               │
  1441→  1441→├─────────────────────────────────────────────────────────────┤
  1442→  1442→│                                                             │
  1443→  1443→│ 상황 (Context):                                              │
  1444→  1444→│   관리자 대시보드를 별도 Next.js 앱으로 분리할지, 기존 키오스크 │
  1445→  1445→│   앱 내에 /admin/* 경로로 통합할지 결정 필요                  │
  1446→  1446→│                                                             │
  1447→  1447→│ 결정 (Decision):                                             │
  1448→  1448→│   기존 Next.js 16 프로세스 내에 /admin/*로 통합              │
  1449→  1449→│                                                             │
  1450→  1450→│ 이유 (Rationale):                                            │
  1451→  1451→│   1. 단일 보드 환경에서 별도 프로세스 실행 시 메모리 추가     │
  1452→  1452→│      (Node.js 프로세스당 ~100MB, 4GB RAM 제약)              │
  1453→  1453→│   2. SQLite 파일 DB는 단일 프로세스에서 접근이 가장 안전      │
  1454→  1454→│      (WAL 모드라도 다중 프로세스 쓰기는 락 경합 발생)         │
  1455→  1455→│   3. Prisma Client 싱글톤 공유로 연결 오버헤드 제로          │
  1456→  1456→│   4. Next.js 16 App Router의 file-system 라우팅이            │
  1457→  1457→│      /admin/* 경로 분리를 자연스럽게 지원                     │
  1458→  1458→│   5. 배포 복잡도 최소화 (단일 빌드, 단일 프로세스, 단일 포트)  │
  1459→  1459→│                                                             │
  1460→  1460→│ 대안 (Alternatives Considered):                              │
  1461→  1461→│   A) 별도 Next.js 앱 (admin.example.com)                     │
  1462→  1462→│      → 메모리 2배, SQLite 다중 프로세스 접근, CORS 설정 필요  │
  1463→  1463→│   B) Remix/Admin.js 별도 프레임워크                           │
  1464→  1464→│      → 기술 스택 분산, 유지보수 비용 증가                     │
  1465→  1465→│   C) Next.js Monorepo (Turborepo)                            │
  1466→  1466→│      → 빌드 복잡도 증가, 단일 보드에 오버엔지니어링            │
  1467→  1467→│                                                             │
  1468→  1468→│ 결과 (Consequences):                                         │
  1469→  1469→│   + 단일 프로세스, 단일 포트, 단일 DB 연결                     │
  1470→  1470→│   + 배포 단순 (next build 한 번)                              │
  1471→  1471→│   + 코드 공유 용이 (lib/, components/ui/, stores/)            │
  1472→  1472→│   - 키오스크 번들에 admin 코드가 포함될 수 있음               │
  1473→  1473→│     → Next.js 자동 code splitting으로 완화                    │
  1474→  1474→│   - 한쪽 장애가 다른쪽에 영향 가능                            │
  1475→  1475→│     → Admin API 에러가 Kiosk API에 영향 없음 (독립 라우트)    │
  1476→  1476→│                                                             │
  1477→  1477→│ 상태: Accepted                                               │
  1478→  1478→└─────────────────────────────────────────────────────────────┘
  1479→  1479→```

  1481→  1481→### ADR-D02: WebSocket 대신 HTTP 폴링으로 실시간 동기화
  1482→  1482→
  1483→  1483→```
  1484→  1484→┌─────────────────────────────────────────────────────────────┐
  1485→  1485→│ ADR-D02: HTTP Polling over WebSocket                        │
  1486→  1486→├─────────────────────────────────────────────────────────────┤
  1487→  1487→│                                                             │
  1488→  1488→│ 상황 (Context):                                              │
  1489→  1489→│   관리자가 CMS 콘텐츠를 변경하면 키오스크 프론트엔드에        │
  1490→  1490→│   ≤3초 내 반영되어야 함. WebSocket과 HTTP 폴링 중 선택 필요   │
  1491→  1491→│                                                             │
  1492→  1492→│ 결정 (Decision):                                             │
  1493→  1493→│   3초 간격 HTTP 폴링 + ETag/If-None-Match 캐싱              │
  1494→  1494→│                                                             │
  1495→  1495→│ 이유 (Rationale):                                            │
  1496→  1496→│   1. 단일 키오스크 환경에서 WebSocket의 이점이 제한적          │
  1497→  1497→│      (다중 클라이언트 브로드캐스트 불필요)                    │
  1498→  1498→│   2. WebSocket 서버 구현 복잡도                              │
  1499→  1499→│      (연결 관리, 재연결, 하트비트, 메모리 누수 방지)           │
  1500→  1500→│   3. ETag 기반 폴링은 변경 없을 시 304 응답으로               │
  1501→  1501→│      페이로드 제로 → 대역폭·CPU 최소                          │
  1502→  1502→│   4. 3초 폴링으로 ≤3초 반영 보장 (요구사항 충족)              │
  1503→  1503→│   5. HTTP 폴링은 추가 인프라 없이 Next.js API Route로 구현    │
  1504→  1504→│   6. 키오스크 브라우저의 Service Worker와 충돌 가능성 낮음     │
  1505→  1505→│                                                             │
  1506→  1506→│ 대안 (Alternatives Considered):                              │
  1507→  1507→│   A) WebSocket (ws / socket.io)                              │
  1508→  1508→│      → 실시간성 최고, but 구현 복잡, 메모리 오버헤드           │
  1509→  1509→│   B) Server-Sent Events (SSE)                                │
  1510→  1510→│      → 단방향 실시간, but 연결 유지 오버헤드, 프록시 타임아웃  │
  1511→  1511→│   C) Long Polling                                            │
  1512→  1512→│      → 연결 유지 오버헤드, 구현 복잡도 중간                   │
  1513→  1513→│                                                             │
  1514→  1514→│ 결과 (Consequences):                                         │
  1515→  1515→│   + 구현 단순 (fetch + setInterval)                           │
  1516→  1516→│   + 디버깅 용이 (표준 HTTP 요청)                              │
  1517→  1517→│   + ETag로 변경 없을 시 네트워크 최소                         │
  1518→  1518→│   + 추가 인프라/라이브러리 불필요                              │
  1519→  1519→│   - 최대 3초 지연 (WebSocket은 밀리초 단위)                   │
  1520→  1520→│   - 3초마다 HTTP 요청 발생 (but 304면 페이로드 0)             │
  1521→  1521→│                                                             │
  1522→  1522→│ 폴백 계획:                                                   │
  1523→  1523→│   P2 다중 키오스크 환경에서 WebSocket 도입 검토                │
  1524→  1524→│                                                             │
  1525→  1525→│ 상태: Accepted                                               │
  1526→  1526→└─────────────────────────────────────────────────────────────┘
  1527→  1527→```

  1529→  1529→### ADR-D03: 세션 기반이 아닌 JWT 기반 관리자 인증
  1530→  1530→
  1531→  1531→```
  1532→  1532→┌─────────────────────────────────────────────────────────────┐
  1533→  1533→│ ADR-D03: JWT over Server-Side Session                       │
  1534→  1534→├─────────────────────────────────────────────────────────────┤
  1535→  1535→│                                                             │
  1536→  1536→│ 상황 (Context):                                              │
  1537→  1537→│   관리자 인증에 서버 측 세션 (express-session 등)과          │
  1538→  1538→│   JWT 중 선택 필요                                           │
  1539→  1539→│                                                             │
  1540→  1540→│ 결정 (Decision):                                             │
  1541→  1541→│   JWT (Access Token 15분 + Refresh Token 7일)                │
  1542→  1542→│   httpOnly 쿠키에 저장                                       │
  1543→  1543→│                                                             │
  1544→  1544→│ 이유 (Rationale):                                            │
  1545→  1545→│   1. Stateless 인증 → 서버 측 세션 스토리지 불필요           │
  1546→  1546→│      (SQLite에 세션 테이블 추가 불필요, 메모리 절약)          │
  1547→  1547→│   2. SQLite 기반 세션 스토리지는 매 요청마다 DB 조회 발생     │
  1548→  1548→│      → JWT는 토큰 검증만으로 인증 완료 (DB 조회 0회)          │
  1549→  1549→│   3. Access Token 짧은 수명 (15분)으로 탈취 피해 최소화       │
  1550→  1550→│   4. Refresh Token으로 자동 갱신, 사용자 경험 유지             │
  1551→  1551→│   5. httpOnly + Secure + SameSite=Strict 쿠키로              │
  1552→  1552→│      XSS·CSRF 방어                                           │
  1553→  1553→│   6. Single-process 환경에서 세션 동기화 불필요                │
  1554→  1554→│                                                             │
  1555→  1555→│ 대안 (Alternatives Considered):                              │
  1556→  1556→│   A) Server-side Session (SQLite-backed)                     │
  1557→  1557→│      → 매 요청 DB 조회, 세션 만료 처리 복잡                   │

  1577→  1577→### ADR-D04: CmsContent Key-Value 테이블 구조 (개별 테이블 분리 안 함)
  1578→  1578→
  1579→  1579→```
  1580→  1580→┌─────────────────────────────────────────────────────────────┐
  1581→  1581→│ ADR-D04: CmsContent Key-Value Table                         │
  1582→  1582→├─────────────────────────────────────────────────────────────┤
  1583→  1583→│                                                             │
  1584→  1584→│ 상황 (Context):                                              │
  1585→  1585→│   CMS 콘텐츠를 화면별 개별 테이블 (IdleContent, MenuContent  │
  1586→  1586→│   등)로 분리할지, 단일 Key-Value 테이블로 통합할지 결정 필요   │
  1587→  1587→│                                                             │
  1588→  1588→│ 결정 (Decision):                                             │
  1589→  1589→│   단일 CmsContent 테이블 (key-value 구조)                    │
  1590→  1590→│   key: "idle.title_text", "menu.borrow_button_color" 등      │
  1591→  1591→│                                                             │
  1592→  1592→│ 이유 (Rationale):                                            │
  1593→  1593→│   1. CMS 항목이 지속적으로 추가/변경되는 환경에서             │
  1594→  1594→│      스키마 마이그레이션 최소화 (새 키는 INSERT만)             │
  1595→  1595→│   2. 키오스크 폴링이 단일 쿼리로 전체 콘텐츠 조회 가능        │
  1596→  1596→│      → N개 테이블이면 N개 쿼리 필요                           │
  1597→  1597→│   3. ETag 생성이 단일 테이블의 updatedAt로 간단               │
  1598→  1598→│   4. 감사 로그가 key 단위로 기록되어 세밀한 추적 가능          │
  1599→  1599→│   5. Strapi/Payload CMS의 single-type 패턴과 유사             │
  1600→  1600→│   6. SQLite에서 다수의 소형 테이블보다 단일 테이블이 효율적   │
  1601→  1601→│                                                             │
  1602→  1602→│ 대안 (Alternatives Considered):                              │
  1603→  1603→│   A) 화면별 개별 테이블 (IdleContent, MenuContent, …)        │
  1604→  1604→│      → 타입 안전성 높음, but 마이그레이션 빈번, 폴링 복잡      │
  1605→  1605→│   B) JSON 컬럼 1개에 전체 콘텐츠 저장                         │
  1606→  1606→│      → 가장 단순, but 부분 업데이트 어려움, 감사 로그 부실     │
  1607→  1607→│   C) Entity-Attribute-Value (EAV) 패턴                       │
  1608→  1608→│      → 유연성 최고, but 조인 복잡, 쿼리 성능 저하              │
  1609→  1609→│                                                             │
  1610→  1610→│ 결과 (Consequences):                                         │
  1611→  1611→│   + 스키마 변경 없이 새 CMS 항목 추가 (INSERT만)              │
  1612→  1612→│   + 단일 쿼리로 전체 콘텐츠 조회 (키오스크 폴링 효율)        │
  1613→  1613→│   + key 단위 감사 로그                                       │
  1614→  1614→│   - 타입 안전성 약화 (value가 항상 String)                    │
  1615→  1615→│     → cms-schema.ts로 key→type 매핑을 앱 레벨에서 보강        │
  1616→  1616→│   - SQLite text 컬럼에 숫자/boolean을 String으로 캐스트        │
  1617→  1617→│     → cms.ts 헬퍼에서 타입 변환 함수 제공                     │
  1618→  1618→│                                                             │
  1619→  1619→│ CmsContent 테이블 구조:                                      │
  1620→  1620→│   id         String   @id @default(uuid())                   │
  1621→  1621→│   key        String   @unique  // "idle.title_text"          │
  1622→  1622→│   type       String            // "text"|"image"|"color"|... │
  1623→  1623→│   value      String            // 값 (타입별 포맷 상이)        │
  1624→  1624→│   updatedAt  DateTime @updatedAt                              │
  1625→  1625→│   updatedBy  String            // AdminUser.id                │
  1626→  1626→│                                                             │
  1627→  1627→│ 상태: Accepted                                               │
  1628→  1628→└─────────────────────────────────────────────────────────────┘

  1636→  1636→├─────────────────────────────────────────────────────────────┤
  1637→  1637→│                                                             │
  1638→  1638→│ 상황 (Context):                                              │
