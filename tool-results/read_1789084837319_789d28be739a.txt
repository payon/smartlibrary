   139→## 3. 신규 테이블 상세 설계
   140→
   141→### 3.1 AdminUser — 관리자 계정
   142→
   143→관리자 대시보드에 로그인하는 모든 계정을 관리한다. RBAC(Role-Based Access Control)의 주체 엔티티이다.
   144→
   145→| 컬럼 | 타입 | 제약 | 기본값 | 설명 |
   146→|------|------|------|--------|------|
   147→| id | String | **PK**, cuid() | 자동 생성 | 관리자 고유 ID |
   148→| email | String | **UNIQUE**, NOT NULL | — | 로그인 이메일 |
   149→| passwordHash | String | NOT NULL | — | bcrypt 해시 (cost=12) |
   150→| name | String | NOT NULL | — | 표시 이름 |
   151→| role | String | NOT NULL | "operator" | 권한 등급: `super_admin` / `admin` / `operator` |
   152→| isActive | Boolean | NOT NULL | true | 계정 활성 여부 (비활성 시 로그인 불가) |
   153→| lastLoginAt | DateTime | nullable | null | 마지막 로그인 시각 |
   154→| createdAt | DateTime | NOT NULL | now() | 생성 시각 |
   155→| updatedAt | DateTime | NOT NULL | @updatedAt | 갱신 시각 |
   156→
   157→**관계**:
   158→- `AdminUser 1:N AuditLog` — 관리자의 모든 감사 로그
   159→- `AdminUser 1:N CmsContent` — CMS 콘텐츠 최종 수정자
   160→- `AdminUser 1:N CmsImage` — 이미지 업로더
   161→- `AdminUser 1:N Notice` — 공지 작성자
   162→
   163→**비즈니스 규칙**:
   164→- `super_admin` 계정은 최소 1개 존재해야 함 (시드 데이터로 보장)
   165→- `email` 형식은 애플리케이션 레이어에서 검증 (Prisma 수준에서는 String)
   166→- 비밀번호는 평문 저장 절대 금지 — 반드시 bcrypt hash
   167→- `isActive = false`인 계정은 인증 미들웨어에서 차단
   168→
   169→---
   170→
   171→### 3.2 AdminRole — 권한 역할 정의
   172→
   173→세분화된 권한(permission)을 역할 단위로 그룹화한다. `AdminUser.role`과 연계되어 사용된다.
   174→
   175→| 컬럼 | 타입 | 제약 | 기본값 | 설명 |
   176→|------|------|------|--------|------|
   177→| id | String | **PK**, cuid() | 자동 생성 | 역할 고유 ID |
   178→| name | String | **UNIQUE**, NOT NULL | — | 역할 식별자 (예: `super_admin`, `admin`, `operator`) |
   179→| displayName | String | NOT NULL | — | UI 표시명 (예: "최고 관리자") |
   180→| description | String | nullable | null | 역할 설명 |
   181→| permissions | String | NOT NULL | "[]" | 권한 목록 JSON 배열 (예: `["user:read","user:write","loan:read"]`) |
   182→| createdAt | DateTime | NOT NULL | now() | 생성 시각 |
   183→
   184→**permissions JSON 스키마**:
   185→
   186→```json
   187→{
   188→  "type": "array",
   189→  "items": {
   190→    "type": "string",
   191→    "pattern": "^[a-z]+:(read|write|delete|manage)$"
   192→  },
   193→  "examples": [
   194→    ["user:read", "user:write", "loan:read", "loan:write", "book:read", "book:write", "cms:manage", "system:manage"],
   195→    ["user:read", "loan:read", "book:read"],
   196→    ["loan:read"]
   197→  ]
   198→}
   199→```
   200→
   201→**권한 매트릭스**:
   202→
   203→| 권한 코드 | super_admin | admin | operator |
   204→|-----------|:-----------:|:-----:|:--------:|
   205→| user:read | O | O | O |
   206→| user:write | O | O | X |
   207→| user:delete | O | X | X |
   208→| loan:read | O | O | O |
   209→| loan:write | O | O | O |
   210→| book:read | O | O | O |
   211→| book:write | O | O | X |
   212→| book:delete | O | X | X |
   213→| cms:manage | O | O | X |
   214→| system:manage | O | X | X |
   215→| audit:read | O | O | X |
   216→| kiosk:manage | O | O | X |
   217→

   220→### 3.3 AuditLog — 감사 추적 로그
   221→
   222→관리자 대시보드에서 발생하는 모든 데이터 변경 사항을 기록한다. 복구, 규제 대응, 장애 원인 분석의 핵심 데이터이다.
   223→
   224→| 컬럼 | 타입 | 제약 | 기본값 | 설명 |
   225→|------|------|------|--------|------|
   226→| id | String | **PK**, cuid() | 자동 생성 | 로그 고유 ID |
   227→| adminUserId | String | FK → AdminUser.id, NOT NULL | — | 행위자 관리자 ID |
   228→| action | String | NOT NULL | — | 행위 유형: `create` / `update` / `delete` / `login` / `logout` / `export` |
   229→| entity | String | NOT NULL | — | 대상 엔티티명 (예: `SimUser`, `Book`, `CmsContent`) |
   230→| entityId | String | nullable | null | 대상 엔티티 ID (엔티티가 특정 인스턴스인 경우) |
   231→| oldValue | String | nullable | null | 변경 전 값 JSON (create의 경우 null) |
   232→| newValue | String | nullable | null | 변경 후 값 JSON (delete의 경우 null) |
   233→| ip | String | nullable | null | 클라이언트 IP 주소 |
   234→| userAgent | String | nullable | null | 클라이언트 User-Agent |
   235→| createdAt | DateTime | NOT NULL | now() | 로그 발생 시각 |
   236→
   237→**관계**:
   238→- `AuditLog N:1 AdminUser` — 행위자 참조
   239→
   240→**비즈니스 규칙**:
   241→- AuditLog은 **절대 UPDATE/DELETE 불가** (append-only)
   242→- `oldValue`/`newValue`는 변경된 필드만 포함하는 diff 형식 권장
   243→- 대량 변경(bulk update) 시 행 단위로 개별 AuditLog 레코드 생성
   244→- 90일 이상 된 로그는 아카이브 테이블로 이관 (애플리케이션 배치 잡)
   245→
   246→**AuditLog 예시**:
   247→
   248→```json
   249→{
   250→  "id": "clxyz123",
   251→  "adminUserId": "cladmin001",
   252→  "action": "update",
   253→  "entity": "CmsContent",
   254→  "entityId": "clcms0042",
   255→  "oldValue": "{\"value\": \"#1E40AF\"}",
   256→  "newValue": "{\"value\": \"#2563EB\"}",
   257→  "ip": "192.168.1.100",
   258→  "userAgent": "Mozilla/5.0 (Windows NT 10.0; Win64; x64) ...",
   259→  "createdAt": "2026-03-04T09:15:00.000Z"
   260→}
   261→```
   262→

   265→### 3.4 CmsContent — CMS 콘텐츠 항목
   266→
   267→대시보드 화면의 텍스트, 색상, 수치 등 커스터마이징 가능한 모든 콘텐츠를 key-value 형태로 관리한다. 코드 배포 없이 UI 변경이 가능하다.
   268→
   269→| 컬럼 | 타입 | 제약 | 기본값 | 설명 |
   270→|------|------|------|--------|------|
   271→| id | String | **PK**, cuid() | 자동 생성 | 콘텐츠 고유 ID |
   272→| key | String | **UNIQUE**, NOT NULL | — | 콘텐츠 식별자 (예: `home.heroTitle`, `theme.primaryColor`) |
   273→| screen | String | NOT NULL | — | 소속 화면 (예: `home`, `stats`, `loan`, `book`) |
   274→| type | String | NOT NULL | "text" | 값 타입: `text` / `image` / `color` / `number` / `json` |
   275→| value | String | nullable | null | 현재 값 |
   276→| defaultValue | String | nullable | null | 초기값 (복원 기준) |
   277→| description | String | nullable | null | 항목 설명 (관리자 UI에서 표시) |
   278→| updatedAt | DateTime | NOT NULL | @updatedAt | 최종 갱신 시각 |
   279→| updatedBy | String | FK → AdminUser.id, nullable | null | 최종 수정 관리자 ID |
   280→
   281→**key 네이밍 컨벤션**:
   282→
   283→```
   284→{screen}.{section}.{field}
   285→
   286→예:
   287→  home.heroTitle          — 홈 화면 히어로 타이틀
   288→  home.heroSubtitle       — 홈 화면 히어로 서브타이틀
   289→  theme.primaryColor      — 테마 기본 색상
   290→  theme.secondaryColor    — 테마 보조 색상
   291→  stats.showPeakHour      — 통계 화면 피크 시간 표시 여부
   292→  loan.maxExtendCount     — 대출 연장 최대 횟수
   293→  kiosk.idleTimeout       — 키오스크 유휴 타임아웃(초)
   294→```
   295→
   296→**관계**:
   297→- `CmsContent N:1 AdminUser` — 최종 수정자 참조 (updatedBy)

   302→
   303→대시보드 및 키오스크 화면에 사용되는 이미지 리소스를 관리한다. 파일은 로컬 디스크 또는 OSS에 저장하고, 메타데이터를 DB에서 관리한다.
   304→
   305→| 컬럼 | 타입 | 제약 | 기본값 | 설명 |
   306→|------|------|------|--------|------|
   307→| id | String | **PK**, cuid() | 자동 생성 | 이미지 고유 ID |
   308→| key | String | **UNIQUE**, NOT NULL | — | 이미지 식별자 (예: `home.heroBg`, `logo.main`) |
   309→| originalName | String | NOT NULL | — | 원본 파일명 |
   310→| storedPath | String | NOT NULL | — | 저장 경로 (예: `/uploads/cms/2026/03/abc.webp`) |
   311→| mimeType | String | NOT NULL | — | MIME 타입 (예: `image/webp`, `image/png`) |
   312→| sizeBytes | Int | NOT NULL | — | 파일 크기 (바이트) |
   313→| width | Int | nullable | null | 이미지 너비 (px) |
   314→| height | Int | nullable | null | 이미지 높이 (px) |
   315→| alt | String | nullable | null | 대체 텍스트 (접근성) |
   316→| updatedAt | DateTime | NOT NULL | @updatedAt | 최종 갱신 시각 |
   317→| uploadedBy | String | FK → AdminUser.id, nullable | null | 업로드 관리자 ID |
   318→
   319→**비즈니스 규칙**:
   320→- 허용 MIME 타입: `image/jpeg`, `image/png`, `image/webp`, `image/svg+xml`
   321→- 최대 파일 크기: 5MB (애플리케이션 레이어에서 검증)
   322→- 업로드 시 WebP 자동 변환 권장 (SVG 제외)
   323→- 이미지 교체 시 기존 파일은 소프트 삭제 후 30일 경과 시 물리 삭제

   327→### 3.6 KioskDevice — 키오스크 기기 관리
   328→
   329→현장에 설치된 키오스크 단말기의 등록, 상태 모니터링, 원격 설정을 지원한다.
   330→
   331→| 컬럼 | 타입 | 제약 | 기본값 | 설명 |
   332→|------|------|------|--------|------|
   333→| id | String | **PK**, cuid() | 자동 생성 | 기기 고유 ID |
   334→| name | String | NOT NULL | — | 기기 표시명 (예: "1층 로비 A") |
   335→| location | String | NOT NULL | — | 설치 위치 (예: "1층 로비", "3층 아동실") |
   336→| ipAddress | String | nullable | null | 기기 IP 주소 |
   337→| status | String | NOT NULL | "offline" | 상태: `online` / `offline` / `maintenance` |
   338→| lastHeartbeat | DateTime | nullable | null | 마지막 heartbeat 수신 시각 |
   339→| settings | String | nullable | null | 기기별 설정 JSON (예:idle 타임아웃, 볼륨 등) |
   340→| createdAt | DateTime | NOT NULL | now() | 등록 시각 |
   341→
   342→**settings JSON 스키마**:
   343→
   344→```json
   345→{
   346→  "type": "object",
   347→  "properties": {
   348→    "idleTimeout": { "type": "number", "default": 120, "description": "유휴 타임아웃 (초)" },
   349→    "volume": { "type": "number", "default": 80, "minimum": 0, "maximum": 100 },
   350→    "brightness": { "type": "number", "default": 100, "minimum": 0, "maximum": 100 },
   351→    "autoRestart": { "type": "boolean", "default": true },
   352→    "restartHour": { "type": "number", "default": 3, "minimum": 0, "maximum": 23 }
   353→  }
   354→}
   355→```
   356→
   357→**비즈니스 규칙**:
   358→- heartbeat: 키오스크가 30초 간격으로 PATCH 요청 → `lastHeartbeat` 갱신, `status = "online"`
   359→- `lastHeartbeat`가 2분 이상 갱신 없으면 → `status = "offline"` (서버 사이드 감지)
   360→- `maintenance` 상태는 관리자가 수동 설정 → 해당 기기 서비스 중단 페이지 표시

   364→### 3.7 SystemSetting — 시스템 설정
   365→
   366→시스템 전반에 걸친 설정 항목을 category + key 복합 유일 키로 관리한다. `CmsContent`가 화면 커스터마이징이라면, `SystemSetting`은 백엔드 로직 제어에 사용된다.
   367→
   368→| 컬럼 | 타입 | 제약 | 기본값 | 설명 |
   369→|------|------|------|--------|------|
   370→| id | String | **PK**, cuid() | 자동 생성 | 설정 고유 ID |
   371→| category | String | NOT NULL | — | 설정 카테고리 (예: `loan`, `kiosk`, `notification`) |
   372→| key | String | NOT NULL | — | 설정 키 (카테고리 내 유일) |
   373→| value | String | nullable | null | 현재 값 |
   374→| defaultValue | String | nullable | null | 초기값 |
   375→| type | String | NOT NULL | "string" | 값 타입: `string` / `number` / `boolean` / `json` |
   376→| description | String | nullable | null | 설정 설명 |
   377→| updatedAt | DateTime | NOT NULL | @updatedAt | 갱신 시각 |
   378→
   379→**유일 제약**: `@@unique([category, key])` — 동일 카테고리 내 키 중복 불가
   380→
   381→**설정 항목 예시**:
   382→
   383→| category | key | defaultValue | type | 설명 |
   384→|----------|-----|-------------|------|------|
   385→| loan | maxLoanCount | "5" | number | 1인 최대 대출 권수 |
   386→| loan | loanPeriodDays | "14" | number | 기본 대출 기간 (일) |
   387→| loan | extendDays | "7" | number | 연장 기간 (일) |
   388→| loan | maxExtendCount | "2" | number | 최대 연장 횟수 |
   389→| kiosk | heartbeatIntervalSec | "30" | number | heartbeat 간격 (초) |
   390→| kiosk | offlineThresholdSec | "120" | number | 오프라인 판정 임계값 (초) |
   391→| notification | overdueReminderDay | "3" | number | 연체 알림 시작일 |
   392→| notification | smtpEnabled | "false" | boolean | SMTP 알림 사용 여부 |

   396→### 3.8 Notice — 공지/알림
   397→
   398→관리자가 작성하는 공지사항으로, 대시보드 및 키오스크 화면에 표시된다.
   399→
   400→| 컬럼 | 타입 | 제약 | 기본값 | 설명 |
   401→|------|------|------|--------|------|
   402→| id | String | **PK**, cuid() | 자동 생성 | 공지 고유 ID |
   403→| title | String | NOT NULL | — | 제목 |
   404→| content | String | NOT NULL | — | 본문 (Markdown 지원) |
   405→| type | String | NOT NULL | "info" | 유형: `info` / `warning` / `urgent` |
   406→| isActive | Boolean | NOT NULL | true | 활성 여부 |
   407→| startAt | DateTime | NOT NULL | now() | 게시 시작 시각 |
   408→| endAt | DateTime | nullable | null | 게시 종료 시각 (null = 무기한) |
   409→| createdAt | DateTime | NOT NULL | now() | 생성 시각 |
   410→| createdBy | String | FK → AdminUser.id, nullable | null | 작성 관리자 ID |
   411→
   412→**비즈니스 규칙**:
   413→- 화면에 표시할 공지 조회 조건: `isActive = true AND startAt <= now() AND (endAt IS NULL OR endAt > now())`
   414→- `urgent` 타입 공지는 항상 최상단에 표시
   415→- `endAt` 도달 시 자동으로 `isActive = false` 처리 (배치 또는 조회 시 평가)
   416→
   417→---
   418→
   419→### 3.9 DashboardStat — 대시보드 통계 스냅샷
   420→
   421→대시보드 렌더링 성능을 위해, 원시 트랜잭션 데이터(SimLoan 등)를 일 단위로 집계하여 스냅샷으로 저장한다. 실시간 집계 쿼리 부하를 방지한다.
   422→
   423→| 컬럼 | 타입 | 제약 | 기본값 | 설명 |
   424→|------|------|------|--------|------|
   425→| id | String | **PK**, cuid() | 자동 생성 | 통계 고유 ID |
   426→| date | String | NOT NULL | — | 집계 일자 (YYYY-MM-DD, 유일) |
   427→| totalLoans | Int | NOT NULL | 0 | 당일 총 대출 건수 |
   428→| activeLoans | Int | NOT NULL | 0 | 현재 활성 대출 건수 |
   429→| returns | Int | NOT NULL | 0 | 당일 반납 건수 |
   430→| overdue | Int | NOT NULL | 0 | 현재 연체 건수 |
   431→| newUsers | Int | NOT NULL | 0 | 당일 신규 가입자 수 |
   432→| peakHour | Int | nullable | null | 당일 피크 시간대 (0~23) |
   433→| createdAt | DateTime | NOT NULL | now() | 레코드 생성 시각 |
   434→
   435→**유일 제약**: `@@unique([date])` — 일별 단일 스냅샷
   436→
   437→**비즈니스 규칙**:
   438→- 매일 00:05 (KST)에 전일 집계 배치 실행 → upsert
   439→- 대시보드 로딩 시 별도 실시간 쿼리 없이 `DashboardStat`만 조회
   440→- 피크 시간대는 당일 시간별 대출 건수 중 최빈 시간으로 산출
   441→- 최근 30일 데이터는 인메모리 캐시에 유지 (TTL = 5분)

   785→## 6. 인덱스 전략
   786→
   787→### 6.1 인덱스 설계 원칙
   788→
   789→| 원칙 | 설명 |
   790→|------|------|
   791→| **쿼리 주도 설계** | 실제 데이터 접근 패턴(9장)을 기준으로 필요 인덱스만 생성 |
   792→| **SQLite B-Tree** | SQLite는 단일 인덱스당 하나의 B-Tree 사용, 복합 조건은 복합 인덱스로 대응 |
   793→| **쓰기 오버헤드 최소화** | 과도한 인덱스는 INSERT/UPDATE 성능 저하, 핵심 쿼리에만 추가 |
   794→
   795→### 6.2 인덱스 목록
   796→
   797→| 테이블 | 인덱스 | 컬럼 | 유형 | 근거 |
   798→|--------|--------|------|------|------|
   799→| **AuditLog** | `idx_audit_admin` | adminUserId | 단일 | 관리자별 감사 로그 조회 |
   800→| **AuditLog** | `idx_audit_entity` | entity, entityId | 복합 | 특정 엔티티 변경 이력 추적 |
   801→| **AuditLog** | `idx_audit_action` | action | 단일 | 행위 유형별 필터링 |
   802→| **AuditLog** | `idx_audit_created` | createdAt | 단일 | 기간별 감사 로그 조회 (최신순) |
   803→| **CmsContent** | `idx_cms_screen` | screen | 단일 | 화면별 콘텐츠 일괄 조회 |
   804→| **CmsContent** | `idx_cms_type` | type | 단일 | 타입별 필터링 |
   805→| **KioskDevice** | `idx_kiosk_status` | status | 단일 | 온라인/오프라인 기기 필터링 |
   806→| **KioskDevice** | `idx_kiosk_location` | location | 단일 | 위치별 기기 조회 |
   807→| **SystemSetting** | `idx_setting_category` | category | 단일 | 카테고리별 설정 일괄 조회 |
   808→| **Notice** | `idx_notice_active_start` | isActive, startAt | 복합 | 활성 공지 시간 범위 조회 |
   809→| **Notice** | `idx_notice_type` | type | 단일 | 유형별 공지 필터링 |

   811→| **SimLoan** | `idx_loan_status` | status | 단일 | 활성/연체 대출 필터링 |

   813→| **SimLoan** | `idx_loan_book` | bookId | 단일 | 도서별 대출 이력 |

   815→### 6.3 추가 인덱스 (성능 튜닝 단계)
   816→
   817→마이그레이션 부하를 최소화하기 위해, 초기 릴리즈 이후 쿼리 프로파일링 결과에 따라 추가를 검토한다.

   823→| `LearningProgress(userId, scenarioId)` | 사용자-시나리오 조합 조회 지연 시 |

   928→
   929→```
   930→Phase 1                    Phase 2                    Phase 3

   932→───────────────          ─────────────────          ──────────────

   940→```bash

   944→  --create-only

   946→# 2. 생성된 SQL 검토
   947→cat prisma/migrations/*/migration.sql

   949→# 3. 시드 스크립트 작성
   950→#    prisma/seed.ts 에 AdminRole, AdminUser, SystemSetting, CmsContent, KioskDevice 시드 추가

  1340→async function getSetting<T>(category: string, key: string): Promise<T | null> {
  1341→  const setting = await prisma.systemSetting.findUnique({
  1342→    where: { category_key: { category, key } },
  1343→  });

  1347→    case 'boolean': return (setting.value === 'true') as unknown as T;
  1348→    case 'json': return JSON.parse(setting.value) as T;
  1349→    default: return setting.value as unknown as T;
  1350→  }
  1351→}

  1408→## 10. 성능 고려사항
  1409→
  1410→### 10.1 SQLite 특성 기반 최적화
  1411→
  1412→| 항목 | 전략 |
  1413→|------|------|
  1414→| **동시 쓰기** | SQLite는 단일 writer. 대량 INSERT는 트랜잭션으로 묶어 lock 횟수 최소화 |
  1415→| **읽기 동시성** | WAL 모드 사용 시 읽기-쓰기 동시 가능. 기본으로 활성화 |
  1416→| **JSON 컬럼** | SQLite는 JSON 함수 지원. 단, WHERE 조건에서 JSON 내부 필드 탐색은 인덱스 미적용 → 애플리케이션 레이어에서 필터링 |
  1417→| **COUNT 쿼리** | 대량 데이터에서 COUNT(*)는 풀 스캔. `DashboardStat` 스냅샷 활용 |
  1418→| **커넥션 풀** | Prisma 기본 풀 크기 = num_cpus * 2 + 1. SQLite는 단일 파일이므로 과도한 풀 크기는 의미 없음 |
  1419→
  1420→### 10.2 대시보드 로딩 최적화
  1421→
  1422→```
  1423→요청 → 인메모리 캐시 확인 (TTL 5분)
  1424→         │ Hit  → 캐시 데이터 반환
  1425→         │ Miss → DashboardStat 조회 + 실시간 보정 쿼리
  1426→                 → 캐시 저장 → 반환
  1427→```
  1428→
  1429→- 첫 화면 로딩: `DashboardStat` 최근 30건 + 활성 대출/연체 COUNT (2건) = **3 쿼리**
  1430→- 상세 화면: 개별 테이블 조회 (페이지네이션, take=50)
  1431→

  1444→  let cursor: string | undefined;
  1445→  while (true) {
  1446→    const batch = await prisma.simUser.findMany({
  1447→      take: 1000,
  1448→      ...(cursor ? { skip: 1, cursor: { id: cursor } } : {}),
  1449→      orderBy: { id: 'asc' },

  1451→    if (batch.length === 0) break;
  1452→    yield batch;

  1462→### 11.1 비밀번호 저장
  1463→
  1464→| 항목 | 정책 |
  1465→|------|------|
  1466→| 해시 알고리즘 | bcrypt (cost factor = 12) |
  1467→| 평문 저장 | **절대 금지** |

  1469→| 초기 비밀번호 | 시드 비밀번호는 첫 로그인 시 강제 변경 |
  1470→
  1471→### 11.2 감사 로그 보호
  1472→
  1473→- AuditLog 테이블에 대한 UPDATE/DELETE 권한은 **애플리케이션 레이어에서 차단**
  1474→- Prisma 미들웨어로 AuditLog 대상 update/delete 작업 시 에러 throw
  1475→- DB 수준에서는 추가 보호 불가 (SQLite는 행 수준 보안 미지원)
  1476→
  1477→```typescript
  1478→// Prisma 미들웨어 — AuditLog 쓰기 금지
  1479→prisma.$use(async (params, next) => {
  1480→  if (params.model === 'AuditLog' && params.action !== 'create' && params.action !== 'findMany' && params.action !== 'findUnique' && params.action !== 'count') {
  1481→    throw new Error('AuditLog은 append-only입니다. UPDATE/DELETE가 금지됩니다.');
  1482→  }
  1483→  return next(params);
  1484→});
  1485→```

  1492→  const admin = await prisma.adminUser.findUnique({
  1493→    where: { id: adminId },
  1494→    select: { role: true, isActive: true },
