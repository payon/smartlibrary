    27→## 1. 시스템 전체 구조
    28→
    29→### 1.1 아키텍처 개요
    30→
    31→백엔드 관리자 대시보드는 기존 스마트 도서관 키오스크 시뮬레이터(Next.js 16, port 3000) 내에 **`/admin/*` 경로로 통합**되는 모듈이다. 별도 프로세스나 포트 없이 동일한 SQLite 데이터베이스와 Prisma 클라이언트를 공유하며, 관리자가 변경한 CMS 콘텐츠가 키오스크 프론트엔드에 폴링 기반 실시간 동기화로 반영되는 구조를 갖는다.
    32→

   343→## 3. 데이터 흐름 아키텍처
   344→
   345→### 3.1 콘텐츠 편집 흐름 (Admin UI → API → DB → Cache → Kiosk)
   346→
   347→```
   348→┌──────────────┐    ① PATCH 요청    ┌───────────────────────┐    ② Prisma WRITE    ┌──────────────┐
   349→│  Admin UI    │ ─────────────────► │ /api/admin/content/   │ ───────────────────► │  CmsContent  │
   350→│  (편집 폼)   │                    │ :key                   │                      │  (SQLite)    │
   351→│              │ ◄──────────────── │                        │                      └──────┬───────┘
   352→│  ⑥ 토스트    │    ③ 200 OK       │  ③' AuditLog 기록     │                             │
   353→│  "저장됨"    │                    │      + 캐시 갱신       │                             │
   354→└──────────────┘                    └───────────────────────┘                             │
   355→                                                                                          │ ④ content-cache
   356→                                                                                          │   version++
   357→                                                                                          ▼
   358→                                                                                 ┌──────────────────┐
   359→                                                                                 │ Content Cache    │
   360→                                                                                 │ (인메모리)        │
   361→                                                                                 │ version: N       │
   362→                                                                                 │ data: Map<key,  │
   363→                                                                                 │   value>         │
   364→                                                                                 └────────┬─────────┘
   365→                                                                                          │
   366→                                                    ⑤ 키오스크 폴링 (30s)                  │
   367→┌──────────────┐    ⑧ Re-render   ┌───────────────┐    ⑦ Zustand set()    ┌───────▼────────┐
   368→│  Kiosk UI    │ ◄────────────── │  useCmsStore   │ ◄────────────────── │  GET /api/content│
   369→│  (IdleScreen │                  │  (Zustand)     │    ⑥ JSON + ETag    │  (If-None-Match)│
   370→│   etc.)      │                  └───────────────┘                      └────────────────┘
   371→└──────────────┘
   372→```
   373→
   374→| 단계 | 설명 | 지연 |
   375→|------|------|------|
   376→| ① | 관리자가 편집 폼에서 값 변경 후 "저장" 클릭 | 사용자 액션 |
   377→| ② | Admin API가 Prisma로 `CmsContent` 테이블에 UPSERT | ~5ms |
   378→| ③ | API가 `AuditLog`에 변경 전후값 기록 + 응답 200 OK | ~3ms |
   379→| ③' | `content-cache.ts` 인메모리 캐시 갱신 + version++ | ~1ms |
   380→| ④ | 캐시 버전 카운터 증분, ETag 값 변경 | ~0ms |
   381→| ⑤ | 키오스크 프론트엔드가 30초 간격으로 `GET /api/content` 폴링 | ≤30s |
   382→| ⑥ | 서버가 ETag 비교, 변경 시 200 + 새 데이터, 미변경 시 304 | ~2ms |
   383→| ⑦ | Zustand `useCmsStore.setCmsContent()` 호출로 전역 상태 갱신 | ~1ms |
   384→| ⑧ | React가 상태 변경 감지, 해당 CMS 값을 사용하는 컴포넌트만 Re-render | ~16ms |
   385→
   386→**총 전파 지연**: CMS 저장 후 **≤30초** 내 키오스크 화면에 반영 (ETag 기반 최적화 시 변경 즉시 응답)
   387→
   388→### 3.2 RBAC 인증·인가 흐름 (Login → Session → Role Check → Permission Gate)
   389→
   390→```
   391→┌──────────────┐    ① POST          ┌───────────────────────┐    ② bcrypt 비교     ┌──────────────┐
   392→│  Login Page  │ ─────────────────► │ /api/admin/auth/      │ ─────────────────► │  AdminUser   │
   393→│  (이메일+PW) │                    │ login                  │                    │  (SQLite)    │
   394→│              │                    │                        │ ◄──────────────── │  passwordHash │
   395→│              │                    │                        │    ③ 일치 여부      └──────────────┘
   396→│              │                    │  ④ JWT 발급            │
   397→│              │ ◄──────────────── │  {accessToken,         │
   398→│              │    Set-Cookie     │   refreshToken}        │
   399→│              │    (httpOnly)     │                        │
   400→└──────────────┘                    └───────────────────────┘
   401→       │
   402→       │ ⑤ 이후 모든 Admin API 요청
   403→       ▼
   404→┌──────────────────────────────────────────────────────────────────────────────┐
   405→│  Request: GET /api/admin/content                                            │
   406→│  Cookie: token=<JWT>                                                        │
   407→│                                                                             │
   408→│  ┌─────────┐    ⑥ JWT 검증     ┌──────────────┐    ⑦ 권한 확인   ┌────────┐│
   409→│  │Middleware│ ──────────────► │  admin-auth.ts│ ─────────────► │ RBAC   ││
   410→│  │  (Next)  │                  │  verifyJWT()  │                │ Table  ││
   411→│  └─────────┘                    └──────────────┘                └────────┘│
   412→│       │                                                              │     │
   413→│       │  ⑧ 응답                                        ⑨ 허용/거부  │     │
   414→│       ▼                                                              ▼     │
   415→│  ┌───────────────┐                                          ┌─────────────┐│
   416→│  │ 200 + Data    │ (권한 있음)                               │ 403         ││
   417→│  └───────────────┘                                          │ Forbidden   ││
   418→│                                                              └─────────────┘│
   419→└──────────────────────────────────────────────────────────────────────────────┘
   420→```
   421→
   422→| 단계 | 설명 |
   423→|------|------|
   424→| ① | 로그인 페이지에서 이메일 + 비밀번호 입력 후 제출 |
   425→| ② | 서버가 `AdminUser` 테이블에서 이메일로 계정 조회 후 bcrypt 비교 |
   426→| ③ | 비밀번호 일치 여부 확인 (5회 실패 시 15분 잠금) |
   427→| ④ | JWT Access Token (15분) + Refresh Token (7일) 발급 |
   428→| ⑤ | httpOnly 쿠키에 토큰 저장, 이후 모든 Admin API 요청에 자동 첨부 |
   429→| ⑥ | Next.js 미들웨어에서 JWT 서명 검증 + 만료 확인 |
   430→| ⑦ | `admin-auth.ts`에서 페이로드의 role 추출 후 요청 API의 필요 권한과 비교 |
   431→| ⑧ | 권한 충족 시 200 OK + 데이터 응답 |
   432→| ⑨ | 권한 부족 시 403 Forbidden 응답 |

   434→### 3.3 감사 로그 흐름 (Action → Middleware → Audit Table)
   435→
   436→```
   437→┌─────────────────────────────────────────────────────────────────────┐
   438→│                     Admin API Request                                │
   439→│  PATCH /api/admin/content/:key  { value: "새 텍스트" }              │
   440→└──────────────────────────┬──────────────────────────────────────────┘
   441→                           │
   442→                           ▼
   443→┌──────────────────────────────────────────────────────────────────────┐
   444→│  ① Route Handler 실행                                                │
   445→│     - 기존값 조회: oldValue = GET CmsContent WHERE key = :key        │
   446→│     - 새값 적용: UPSERT CmsContent SET value = "새 텍스트"          │
   447→└──────────────────────────┬───────────────────────────────────────────┘
   448→                           │
   449→                           ▼
   450→┌──────────────────────────────────────────────────────────────────────┐
   451→│  ② audit-logger.ts 기록                                              │
   452→│     AuditLog.create({                                                │
   453→│       action:    "UPDATE",                                           │
   454→│       entity:    "CmsContent",                                       │
   455→│       entityId:  ":key",                                             │
   456→│       oldValue:  JSON.stringify(oldValue),    // 변경 전              │
   457→│       newValue:  JSON.stringify("새 텍스트"), // 변경 후              │
   458→│       performedBy: adminUser.id,                                     │
   459→│       performedAt: new Date()                                        │
   460→│     })                                                               │
   461→└──────────────────────────┬───────────────────────────────────────────┘
   462→                           │
   463→                           ▼
   464→┌──────────────────────────────────────────────────────────────────────┐
   465→│  ③ AuditLog 테이블 (SQLite)                                         │
   466→│  ┌──────────┬────────┬───────────┬─────────┬──────────┬────────────┐│
   467→│  │ action   │ entity │ entityId  │ oldValue│ newValue │ performedBy││
   468→│  ├──────────┼────────┼───────────┼─────────┼──────────┼────────────┤│
   469→│  │ UPDATE   │ CmsCont│ idle.title│ "스마트  │ "성북구   │ admin-001  ││
   470→│  │          │ ent    │ _text     │ 도서관  │ 도서관"  │            ││
   471→│  └──────────┴────────┴───────────┴─────────┴──────────┴────────────┘│
   472→└──────────────────────────────────────────────────────────────────────┘
   473→```

   719→#### PermissionGate 컴포넌트
   720→
   721→```typescript
   722→// UI 요소의 표시/숨김을 RBAC 권한으로 제어
   723→function PermissionGate({
   724→  requiredRole,
   725→  children,
   726→  fallback = null
   727→}: {
   728→  requiredRole: 'super_admin' | 'admin' | 'operator';
   729→  children: React.ReactNode;
   730→  fallback?: React.ReactNode;
   731→}) {
   732→  const { user } = useAdminStore();
   733→  const hasPermission = checkPermission(user.role, requiredRole);
   734→  return hasPermission ? <>{children}</> : <>{fallback}</>;
   735→}
   736→
   737→// 사용 예:
   738→<PermissionGate requiredRole="admin">
   739→  <Button onClick={handleSave}>저장</Button>
   740→</PermissionGate>
   741→
   742→<PermissionGate requiredRole="super_admin">
   743→  <BackupRestore />
   744→</PermissionGate>
   745→```

   747→#### AdminGuard 컴포넌트
   748→
   749→```typescript
   750→// 인증되지 않은 사용자를 로그인 페이지로 리다이렉트
   751→export default function AdminGuard({ children }: { children: React.ReactNode }) {
   752→  const { isAuthenticated, checkSession } = useAdminStore();
   753→
   754→  useEffect(() => {
   755→    checkSession(); // GET /api/admin/auth/me
   756→  }, []);
   757→
   758→  if (!isAuthenticated) {
   759→    redirect('/admin/login');
   760→    return null;
   761→  }
   762→
   763→  return <>{children}</>;
   764→}

   844→### 5.2 Admin Route Handler 공통 패턴
   845→
   846→```typescript
   847→// 모든 Admin API Route의 공통 구조
   848→export async function PATCH(
   849→  request: NextRequest,
   850→  { params }: { params: { key: string } }
   851→) {
   852→  // 1. 인증 확인 (JWT)
   853→  const session = await verifyAuth(request);
   854→  if (!session) {
   855→    return NextResponse.json({ error: 'Unauthorized' }, { status: 401 });
   856→  }
   857→
   858→  // 2. 권한 확인 (RBAC)
   859→  if (!hasPermission(session.role, 'content:write')) {
   860→    return NextResponse.json({ error: 'Forbidden' }, { status: 403 });
   861→  }
   862→
   863→  // 3. Rate Limit 확인
   864→  if (!checkRateLimit(session.userId)) {
   865→    return NextResponse.json({ error: 'Too Many Requests' }, { status: 429 });
   866→  }
   867→
   868→  // 4. 입력 검증 (Zod)
   869→  const body = await request.json();
   870→  const validated = contentUpdateSchema.parse(body);
   871→
   872→  // 5. 기존값 조회 (감사 로그용)
   873→  const oldValue = await db.cmsContent.findUnique({ where: { key: params.key } });
   874→
   875→  // 6. 비즈니스 로직 + DB 쓰기
   876→  const result = await db.cmsContent.upsert({
   877→    where: { key: params.key },
   878→    update: { value: validated.value, updatedBy: session.userId },
   879→    create: { key: params.key, type: validated.type, value: validated.value, updatedBy: session.userId },
   880→  });
   881→
   882→  // 7. 콘텐츠 캐시 갱신 + 버전 증분
   883→  contentCache.update(params.key, validated.value);
   884→
   885→  // 8. 감사 로그 기록
   886→  await auditLog({
   887→    action: 'UPDATE',
   888→    entity: 'CmsContent',
   889→    entityId: params.key,
   890→    oldValue: oldValue?.value,
   891→    newValue: validated.value,
   892→    performedBy: session.userId,
   893→  });
   894→
   895→  // 9. 응답 반환
   896→  return NextResponse.json(result, { headers: getSecurityHeaders() });
   897→}
   898→```

   903→// GET /api/content — ETag 기반 변경 감지
   904→export async function GET(request: NextRequest) {
   905→  const currentVersion = contentCache.getVersion();
   906→  const etag = `"v${currentVersion}"`;
   907→
   908→  // If-None-Match 헤더 비교 → 304 Not Modified
   909→  const ifNoneMatch = request.headers.get('if-none-match');
   910→  if (ifNoneMatch === etag) {
   911→    return new NextResponse(null, {
   912→      status: 304,
   913→      headers: { ETag: etag },
   914→    });
   915→  }
   916→
   917→  // 변경 시 전체 콘텐츠 반환
   918→  const content = contentCache.getAll();
   919→  return NextResponse.json(content, {
   920→    headers: {
   921→      ETag: etag,
   922→      'Cache-Control': 'no-cache',
   923→      ...getSecurityHeaders(),
   924→    },
   925→  });
   926→}
   927→```

   931→## 6. 실시간 동기화 아키텍처
   932→
   933→### 6.1 동기화 개요
   934→
   935→관리자 대시보드에서 CMS 콘텐츠를 변경하면, 해당 변경이 **폴링 기반**으로 키오스크 프론트엔드에 전파된다. WebSocket 대신 폴링을 선택한 이유는 단일 키오스크 환경에서 구현 단순성과 안정성이 우선이기 때문이다 (→ ADR-006).
   936→
   937→### 6.2 동기화 아키텍처 다이어그램

   992→### 6.3 버전 관리 메커니즘
   993→
   994→```
   995→시간축:
   996→─────────────────────────────────────────────────────────────────►
   997→
   998→T0: 키오스크 시작 → GET /api/content → version:1, ETag:"v1"
   999→T1: 30초 후 폴링 → GET /api/content (If-None-Match:"v1") → 304 Not Modified
  1000→T2: 관리자 변경 → PATCH /api/admin/content/idle.title_text
  1001→    → DB UPSERT → content-cache.update() → version:2, ETag:"v2"
  1002→T3: 30초 후 폴링 → GET /api/content (If-None-Match:"v1") → 200 + 새 데이터 + ETag:"v2"
  1003→    → Zustand setContent() → 화면 Re-render
  1004→T4: 30초 후 폴링 → GET /api/content (If-None-Match:"v2") → 304 Not Modified
  1005→```

  1007→### 6.4 content-cache.ts 구조
  1008→
  1009→```typescript
  1010→// src/lib/content-cache.ts
  1011→class ContentCache {
  1012→  private cache = new Map<string, string>();
  1013→  private version = 0;
  1014→  private lastUpdatedAt = new Date();
  1015→
  1016→  /** 전체 캐시 조회 (키오스크 API용) */
  1017→  getAll(): { version: number; content: Record<string, string>; updatedAt: string } {
  1018→    return {
  1019→      version: this.version,
  1020→      content: Object.fromEntries(this.cache),
  1021→      updatedAt: this.lastUpdatedAt.toISOString(),
  1022→    };
  1023→  }
  1024→
  1025→  /** 현재 버전 조회 (ETag 생성용) */
  1026→  getVersion(): number {
  1027→    return this.version;
  1028→  }
  1029→
  1030→  /** 단일 항목 조회 */
  1031→  get(key: string): string | undefined {
  1032→    return this.cache.get(key);
  1033→  }
  1034→
  1035→  /** 캐시 갱신 (Admin API 호출 시) */
  1036→  update(key: string, value: string): void {
  1037→    this.cache.set(key, value);
  1038→    this.version++;
  1039→    this.lastUpdatedAt = new Date();
  1040→  }
  1041→
  1042→  /** DB에서 전체 로드 (서버 시작 시) */
  1043→  async loadFromDB(): Promise<void> {
  1044→    const all = await db.cmsContent.findMany();
  1045→    this.cache.clear();
  1046→    for (const item of all) {
  1047→      this.cache.set(item.key, item.value);
  1048→    }
  1049→    this.version = all.length > 0 ? Math.max(...all.map(i => i.updatedAt.getTime())) : 0;
  1050→  }
  1051→}
  1052→
  1053→export const contentCache = new ContentCache();
  1054→```

  1120→### 7.3 admin-auth.ts 구현 구조
  1121→
  1122→```typescript
  1123→// src/lib/admin-auth.ts
  1124→
  1125→// JWT 페이로드 타입
  1126→interface AdminJWTPayload {
  1127→  userId: string;
  1128→  email: string;
  1129→  role: 'super_admin' | 'admin' | 'operator';
  1130→  iat: number;
  1131→  exp: number;
  1132→}
  1133→
  1134→// 권한 체크 함수
  1135→const PERMISSION_MAP: Record<string, string[]> = {
  1136→  'content:write':  ['super_admin', 'admin'],
  1137→  'content:upload': ['super_admin', 'admin'],
  1138→  'books:write':    ['super_admin', 'admin'],
  1139→  'books:delete':   ['super_admin', 'admin'],
  1140→  'users:write':    ['super_admin', 'admin'],
  1141→  'accounts:read':  ['super_admin'],
  1142→  'accounts:write': ['super_admin'],
  1143→  'audit:read':     ['super_admin', 'admin'],
  1144→  'kiosk:control':  ['super_admin'],
  1145→  'backup:execute': ['super_admin'],
  1146→  // 기본 읽기 권한은 모든 역할 허용
  1147→};
  1148→
  1149→function hasPermission(role: string, permission: string): boolean {
  1150→  const allowed = PERMISSION_MAP[permission];
  1151→  if (!allowed) return true; // 정의되지 않은 권한은 모두 허용
  1152→  return allowed.includes(role);
  1153→}
  1154→
  1155→// JWT 검증 (httpOnly 쿠키에서 토큰 추출)
  1156→async function verifyAuth(request: NextRequest): Promise<AdminJWTPayload | null> {
  1157→  const token = request.cookies.get('admin-token')?.value;
  1158→  if (!token) return null;
  1159→  try {
  1160→    const payload = jwt.verify(token, JWT_SECRET) as AdminJWTPayload;
  1161→    return payload;
  1162→  } catch {
  1163→    return null; // 만료 또는 무효
  1164→  }
  1165→}
  1166→
  1167→// JWT 발급
  1168→function issueToken(payload: Omit<AdminJWTPayload, 'iat' | 'exp'>): string {
  1169→  return jwt.sign(payload, JWT_SECRET, { expiresIn: '15m' });
  1170→}
  1171→
  1172→// Refresh Token 발급
  1173→function issueRefreshToken(userId: string): string {
  1174→  return jwt.sign({ userId, type: 'refresh' }, JWT_SECRET, { expiresIn: '7d' });
  1175→}
  1176→```

  1422→## 11. ADR (Architecture Decision Records)
  1423→
  1424→### ADR-001: 동일 Next.js 앱 통합 (별도 앱 분리 불가)
  1425→
  1426→**상황**: 관리자 대시보드를 독립 Next.js 앱으로 분리할지, 기존 키오스크 앱에 통합할지 결정 필요
  1427→
  1428→**결정**: 기존 Next.js 16 앱 내 `/admin/*` 경로로 통합
  1429→
  1430→**이유**:
  1431→- 단일 프로세스로 메모리 절약 (임베디드 보드 제약)
  1432→- SQLite DB 공유가 자연스러움 (동일 Prisma 클라이언트)
  1433→- 배포 복잡도 최소화 (단일 `next build` + `next start`)
  1434→- Next.js App Router의 레이아웃 중첩로 관리자/키오스크 UI 자연스럽게 분리
  1435→
  1436→**결과**: 메모리 효율적, DB 접근 간편, 반면 번들 크기 증가 (Admin 컴포넌트 추가 ~150KB gzip)
  1437→

  1439→
  1440→### ADR-002: 폴링 기반 실시간 동기화 (WebSocket 미채택)
  1441→
  1442→**상황**: 관리자 CMS 변경을 키오스크에 실시간 전파할 방식 선택
  1443→
  1444→**결정**: HTTP 폴링 (30초 간격) + ETag 변경 감지
  1445→
  1446→**이유**:
  1447→- 단일 키오스크 환경에서 WebSocket의 오버엔지니어링
  1448→- HTTP 폴링은 추가 의존성 없이 구현 가능
  1449→- ETag 기반 304 응답으로 대역폭 최소화
  1450→- 서버 재시작 시 WebSocket 재연결 복구 로직 불필요
  1451→- 30초 지연은 도서관 환경에서 허용 가능 (즉각성 요구 낮음)
  1452→
  1453→**결과**: 구현 단순, 안정성 높음, 반면 최대 30초 지연 발생
  1454→
  1455→---
  1456→
  1457→### ADR-003: JWT + httpOnly 쿠키 인증 (Session Storage 미채택)
  1458→
  1459→**상황**: 관리자 인증 방식 선택
  1460→
  1461→**결정**: JWT (Access Token 15분 + Refresh Token 7일)를 httpOnly 쿠키에 저장
  1462→
  1463→**이유**:
  1464→- httpOnly 쿠키는 JavaScript에서 접근 불가 → XSS 공격 방어
  1465→- SameSite=Strict로 CSRF 공격 방어
  1466→- JWT는 무상태(stateless) → 서버 측 세션 저장소 불필요
  1467→- Refresh Token으로 Access Token 만료 시 자동 갱신
  1468→- SQLite 환경에서 세션 테이블 추가 오버헤드 불필요
  1469→
  1470→**결과**: 보안 강화, 서버 무상태, 반면 토큰 갱신 로직 필요
  1471→
  1472→---
  1473→
  1474→### ADR-004: 인메모리 콘텐츠 캐시 (Redis 미채택)
  1475→
  1476→**상황**: 키오스크 폴링 시 콘텐츠 조회 성능 최적화 방식 선택
  1477→
  1478→**결정**: Node.js 인메모리 `Map` 기반 캐시 + 버전 카운터
  1479→
  1480→**이유**:
  1481→- CMS 항목 수 ~50개, 총 용량 < 100KB → 인메모리 충분
  1482→- 외부 Redis 의존성 추가 불필요 (단일 보드 환경)
  1483→- 서버 시작 시 DB에서 1회 로드, 이후 업데이트만 반영
  1484→- 버전 카운터로 ETag 생성, 304 응답으로 폴링 최적화
  1485→
  1486→**결과**: 응답 ~2ms (DB 쿼리 생략), 반면 서버 재시작 시 캐시 리로드 필요

  1490→### ADR-005: 3-tier 고정 역할 (동적 권한 미채택)
  1491→
  1492→**상황**: RBAC 역할을 동적으로 정의할지, 고정 3-tier로 할지 결정
  1493→
  1494→**결정**: `super_admin` / `admin` / `operator` 3개 역할 고정
  1495→
  1496→**이유**:
  1497→- 소규모 도서관 관리팀 (3~5명)에 3-tier면 충분
  1498→- 동적 역할 시 역할 관리 UI + 권한 매핑 테이블 + 마이그레이션 복잡도 증가
  1499→- 코드 내 권한 체크가 컴파일 타임에 결정 가능 → 타입 안전성
  1500→- ADR-003 JWT 페이로드에 role 문자열 직접 포함 가능
  1501→
  1502→**결과**: 구현 단순, 타입 안전, 반면 역할 확장 시 스키마 변경 필요

  1506→### ADR-006: 감사 로그 Append-Only (UPDATE/DELETE 금지)
  1507→
  1508→**상황**: 감사 로그의 수정·삭제 허용 여부 결정
  1509→
  1510→**결정**: AuditLog 테이블은 INSERT만 허용, UPDATE/DELETE 금지
  1511→
  1512→**이유**:
  1513→- 감사 추적 무결성 보장 (규제 대응, 장애 원인 분석)
  1514→- 변조 방지 → 관리자가 실수를 숨길 수 없음
  1515→- SQLite에서 읽기 전용 테이블 보호는 앱 레이어에서만 가능 (Prisma 접근 제한)
  1516→
  1517→**결과**: 감사 무결성 보장, 반면 잘못 기록된 로그 수정 불가
